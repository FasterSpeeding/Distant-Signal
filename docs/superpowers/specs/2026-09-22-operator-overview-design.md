# Operator Overview Feature Area — Specification

This spec covers three new/extended surfaces (A: all-lines dashboard, B: per-line drill-down, C: operators list) plus two cross-cutting concerns (D: history, E: operator pinning), grounded in what already exists in the repo. Citations are file paths; anything I couldn't verify directly is flagged as **Speculative**.

---

## 0. What already exists (baseline)

**Status computation (real-time only, no persisted "current state" beyond `line_status`)**
- `crates/aggregator/src/aggregation.rs`'s `aggregate()` builds one `LineStatusReport` per line every cycle, purely in memory, from incidents (Layer 1) + LDBWS sample inference (Layer 2) + an optional full-coverage merge (Layer 3, `merge_full_coverage`). It is a pure function of a snapshot — nothing here reads or writes "previous status" itself.
- The cycle's output is upserted into `line_status` (one row per line, replaced each cycle) — `crates/api/migrations/20260510023522_initial.sql`.
- A row is written to **`line_status_history`** (append-only, `line_id, statuses JSONB, computed_at`) alongside every upsert, per that same migration's comment ("Useful for debugging regressions and building a 'status over time' view"). Retention is `history_retention_days` (default small, e.g. 7 — see `ServiceArguments::history_retention_days` used throughout `crates/api/src/routes/lines.rs`'s test fixtures).
- **This is already the event-sourced status history D asks about.** It is read by `GET /Line/{id}/Status/{from}/to/{to}` (`frontend/lib/api.ts`'s `getLineStatusHistory`) and rendered by the existing **Timeline tab** of `/lines/[id]/history` (`frontend/app/lines/[id]/history/page.tsx`'s `HistoryResults`, using `frontend/lib/history.ts`'s `groupHistoryByDay`). Nothing new is needed at the per-line raw-event level — it's short-retention (days) but it's there.

**Separately, longer-retention *rollup* stats (delay/cancellation/skip rate, not severity)**
- `line_status_daily_stats`, `line_status_hourly`→half-hourly, `line_status_daily_coverage_stats`, `line_status_half_hourly_coverage_stats` (migrations `20260831090001_line_status_daily_stats.sql` through `20260904100000_full_coverage_line_stats.sql`) are populated by the aggregator from **deduplicated sample data** (`crates/aggregator/src/dedup.rs`, `queries::record_daily_stats`), retained much longer (`daily_stats_retention_days`, `half_hourly_stats_retention_hours` — e.g. 300 days / 840 hours per the test fixtures in `crates/api/src/routes/lines.rs`).
- These feed the **Trends tab** — `frontend/app/lines/[id]/history/TrendsCharts.tsx` (read first, per the task), `TrendsResults.tsx`, `HalfHourlyTrendsResults.tsx`, `CoverageTrendsResults.tsx`, `GranularityControl.tsx`, `HistoryRangePicker.tsx`. This is a **fully built, working mechanism**: half-hour/hour/6-hour/day granularity, retention-ceiling-aware, gap-rendering via `gapSpans`/`ReferenceArea`, a "Trains counted" volume panel. It plots **rate metrics** (delay/cancellation/skip rate, avg delay minutes), not severity/status directly.
- Important distinction for D: **`line_status_history` (Timeline tab) is severity/status-change history; the `*_stats` tables (Trends tab) are throughput/rate history.** They are two different signals at two different retentions, already both built, already both per-line only.

**Frontend conventions confirmed**
- Server Components fetch via `frontend/lib/api.ts` (server-only `API_BASE_URL`), forwarding cookies manually (`cookieForwardInit`) since Server Component `fetch` doesn't inherit them.
- Client Components (like `PinToggle`) call the same-origin `/api/*` proxy (`app/api/[...path]/route.ts`), never `lib/api.ts` directly.
- `getPreferences()` fails closed to `{ pinnedLines: [], pinnedStations: [] }` on a 401 (`frontend/lib/api.ts:309-323`) — the "fails closed to nothing pinned" pattern the task references.
- Reusable pieces directly applicable to A/B/C: `StatusBadge`, `LineStatusCard` (`frontend/components/LineStatusCard.tsx` — card wraps worst status + representative sample summary + last-updated, links to `/lines/{id}`), `StatusRow`, `IssueList` (bucketed active/upcoming/ended issue list with filters, already generalized for "line" vs "station" subjects — see its `IssueListSubject` type), `frontend/lib/severity.ts` (`severityRank`, `worstStatus`, and critically **`GROUP_RANK`/`SeverityGroup`** — `'good'|'informational'|'planned'|'mild'|'severe'` — this is exactly the "good service / minor delays / severe disruption / suspended" bucketing A asks for, already implemented), `frontend/lib/sampleStats.ts` (`representativeStatus`, `formatSampleSummary`), `PinToggle`.

**Operator model (the key finding for C)**
- There is **no operator entity with relationships** anywhere in the schema. `tocs` (`crates/api/migrations/20260706004003_reference_data.sql:27`) is flat reference data — `atoc_code`/`name`/etc, populated by `crates/poller-tocs` from the RDM TOC-list XML (`crates/poller-tocs/src/schema.rs`). It exists purely to resolve a code to a display name (`GET /public/tocs/all` → `frontend/lib/api.ts`'s `getAllTocs()`, consumed by `AllLinesTable.tsx`'s `nameByCode` map).
- **"Operator" is a plain ATOC code string living in a `TEXT[]` `operators` column** on: `LineDefinition` (catalogue TOML, `lines/*.toml` per `DESIGN.md` §5.1), `custom_lines`, and `line_status` (and therefore `LineStatusReport.operators` on the wire). There is no join table, no FK, no "operator → lines" index anywhere in the backend.
- The **only place today that computes "lines for operator X"** is client-side, ad hoc: `AllLinesTable.tsx`'s `operatorOptions`/`expandOperatorForFiltering` derive the operator list from `lines.flatMap(line => line.operators)` and filter rows by `row.line.operators.some(op => expandedSelection.has(op))`. This includes the `TFL_ADJACENT_OPERATORS` widening (`'LO'`, `'XR'` count as TfL) and the special `common::TFL_OPERATOR = "TfL"` constant (`crates/common/src/lib.rs:237`).
- A line can carry **multiple** operators (e.g. shared-trunk lines), so the operator→line relationship is many-to-many, computed by scanning, not stored.
- **Implication for C**: a per-operator rollup has no existing backend primitive to build on. It must be computed by (1) resolving every line whose `operators` array contains the target code (across catalogue + custom + TfL sources, same three sources `list_lines`/`filter_known_pinned_lines` already enumerate — `crates/api/src/routes/lines.rs:379-448`, `crates/api/src/routes/preferences.rs:153-168`), then (2) rolling up each of those lines' current `LineStatus` (worst severity, sample stats) into one summary. Custom lines complicate this: an operator's rollup would need to decide whether to include private custom lines at all (recommendation: exclude them — an operator page is a public reference view, not a personal one; custom lines already have no place in `/public/tocs`-style aggregate reporting).

**Preferences / pinning backend (for E)**
- Table: `pinned_lines(user_id, line_id, pinned_at)`, `pinned_stations(user_id, crs, pinned_at)` — both owner-scoped, no unique-per-line constraint shown but effectively a set (`crates/api/migrations/20260710090000_preferences.sql`, later given `user_id` by `20260828100000_add_ownership.sql`).
- Data layer: `crates/api/src/data/preferences.rs` — `list_pinned_line_ids`, `list_pinned_station_crs`, `filter_existing_station_crs`, `replace_pinned_lines` (delete-all-then-insert-all in one transaction, full-set replace, not per-item), `replace_pinned_stations`.
- Route: `crates/api/src/routes/preferences.rs` — `GET /public/preferences` (session-gated, returns `{pinnedLines, pinnedStations}`, filters stale/unreadable ids via `filter_known_pinned_lines` sourced from catalogue + caller's own readable custom lines + TfL), `PUT /public/preferences/pinned-lines`, `PUT /public/preferences/pinned-stations` (both **validate nothing** on write — filtering happens on read).
- Frontend: `PinToggle` (`frontend/components/PinToggle.tsx`) does read-modify-write against `/api/preferences` + `/api/preferences/pinned-{lines,stations}`, is generic over `kind: 'line' | 'station'`, shows a login-prompt modal on 401, and is deliberately a "last write wins" full-list replace (documented tradeoff, accepted for this app's scale).
- `frontend/app/page.tsx` gates the whole "Your Lines"/"Your Stations" sections on `preferences.pinnedLines.length === 0` / `pinnedStations.length === 0`, defaulting via `NO_PREFERENCES = { pinnedLines: [], pinnedStations: [] }` on any preferences-fetch failure (fail-closed, Decision 5 of `docs/superpowers/specs/2026-07-09-...` per the code comments) — the "You haven't pinned any lines yet" empty-state copy lives at `app/page.tsx:420-423`.

## A. Aggregated all-lines overview page

**What already answers most of this**: `GET /Line/Mode/{mode}/Status` (`getLineStatusForMode`) already returns every line's current `LineStatusReport` in one call, and `frontend/app/page.tsx`'s `notGoodServiceSummary`/`RightNowModule` already computes a "count of lines not at Good Service" + worst-first list from it, unauthenticated-safe. `/lines` (`AllLinesTable.tsx`) already renders every line with a sortable Status column. What's **missing** is a single "at a glance" dashboard view: one glanceable network-health readout (not a 125-row table), grouped by the five severity buckets already defined in `severity.ts`'s `SeverityGroup`, ideally split by mode (National Rail vs TfL) and by country (GB/NI/RoI — `lib/modes.ts`'s `countryForReport`, already used for `AllLinesTable`'s country filter).

**Data model gaps**: none for a real-time-only view — `GROUP_RANK`/`worstStatus`/`severityRank` already exist client-side; the aggregation is a pure client-side reduce over `allReports` (same pattern `notGoodServiceSummary` already uses). No new backend endpoint is required for the *current* snapshot.

**Recommended page**: `frontend/app/status/page.tsx` (or fold into an expanded `/lines` header — see Open Questions). Structure:
- A top strip of five counters (Good / Minor / Severe / Suspended-or-worse / Planned), each a stat tile linking to `/lines` pre-filtered to that bucket (this requires `/lines` to accept a status-group query param, which it doesn't today — `AllLinesTable`'s filter state is local `useState`, not `searchParams`-driven; see Open Questions).
- Below that, the existing `RightNowModule`-style "worst lines right now" list, but unbounded (or reusing `IssueList`'s bucketed-list UX) rather than `RIGHT_NOW_LIMIT`-capped.
- A "by mode" or "by country" breakdown section (National Rail vs TfL, GB vs NI vs RoI) using the same `countryForReport`/`DISPLAYED_MODES_PARAM` machinery `AllLinesTable` and `app/page.tsx` already use.

**Backend/API**: none required for the current-state view. **If** a lightweight "network health at a glance" API is wanted for other consumers (MCP tool, external embed), a thin `GET /public/status/overview` computing the same reduce server-side would avoid shipping all ~125 `LineStatusReport`s to render five numbers — **optional, not required** (frontend-only reduction over the already-fetched `allReports` is the pragmatic Phase-1 choice, same as `notGoodServiceSummary` already does).

## B. Per-line granular pages

**This is largely already built.** `frontend/app/lines/[id]/page.tsx` already shows: worst status + `StatusBadge`, `RepresentativeInfo`, `IssueList` (bucketed disruption list with active/upcoming/ended, per-issue `DisruptionDetail`), operator badges (`operatorLabel`/`tocNameLookup`), TfL counterpart status (`tflStatus`), a "Recent trends" half-hourly chart pair (`HalfHourlyTrendsResults`/`HalfHourlyCoverageTrendsResults`), delete/edit for custom lines, share button. `frontend/app/lines/[id]/history/page.tsx` already provides the Timeline (raw status-change log) + Trends (rate rollups, four granularities) tabs described in §0.

What B is missing relative to the task's "which sections/stations affected" ask:
- **Segment/station-level detail is not separately surfaced today.** The aggregator's `common::matcher` already classifies incidents by `MatchScope` (`ExclusiveSegment`/`SharedSegment`/`StationHit`/`KeywordOnly`/`OperatorOnly` — `DESIGN.md` §5.3) and `Disruption.affected_stops`/`affected_routes` already carry which stations/route-segment are hit (`crates/aggregator/src/aggregation.rs`'s `routes_from_stations`, `status_from_incident`). `DisruptionDetail` component likely already renders `affectedStops`/`affectedRoutes` — **worth verifying and, if not already surfaced, the fix is purely a frontend rendering gap, not a data gap.** No new backend work needed.
- **"Which trains"** — `GET /public/lines/{id}/trains?date=` already exists (`crates/api/src/routes/lines.rs:261-319`, `get_line_trains`) returning every scheduled UID for a rail day joined with live status. This is not currently linked from `/lines/[id]` — a plausible small addition (a "Trains today" tab/section) rather than new backend work.

**Recommendation for B**: no new data model or backend work; the gap is presentation — add a "Trains running today" panel to `/lines/[id]` backed by the existing `get_line_trains` route, and confirm/extend `DisruptionDetail`'s rendering of `affectedStops`/`affectedRoutes` per status (segment-level detail already exists in the `Disruption` JSON per `frontend/lib/types.ts`'s `Disruption` type).

## C. Operators list page

**No backend primitive exists for this at all** (see §0's operator-model finding) — this is the biggest net-new piece.

**Data model gap**: need a way to enumerate "the set of operators" and, per operator, "the lines that operator runs." Two viable approaches:

1. **Computed, no new tables** (recommended for Phase 1): a new endpoint `GET /public/operators` that:
   - Reads `GET /public/tocs/all`-equivalent reference data (`tocs` table) for code→name.
   - Cross-references every line (catalogue `app.config.lines` + TfL rows from `queries::tfl_line_summaries`, **excluding private custom lines** — this is a public aggregate view) for `operators.contains(code)`.
   - For each operator, pulls the current `LineStatus` for every matching line (a batched `line_status` read, same shape `queries::tfl_line_summaries`/`list_lines` already do) and computes a rollup: worst severity across those lines (reuse `common::severity_rank`/its frontend mirror `severityRank`), and an aggregate delay/cancellation/skip rate (reuse the same `SampleStats` averaging `compute_sample_stats` in `crates/common/src/lib.rs` already implements per-line — extended to sum across an operator's lines).
   - This is pure computation over already-materialized data — no new table needed for the *current-state* rollup.

2. **Only necessary if per-operator status needs to be queried historically or filtered server-side at scale**: a real `operators`/`toc` reference table already exists (it just isn't joined to anything); adding a **materialized `operator_status` table**, refreshed by the aggregator each cycle the same way `line_status` is, would let history/trend queries run directly instead of re-deriving from N lines' rollups every request. This is the natural extension point for D (see below) but is **not required to ship C** — Phase 1 can compute the rollup live on each `GET /public/operators` request as long as the line count per operator stays small (it does — even SWR/Northern-scale multi-route operators are single-digit-to-low-teens lines).

**Which crate**: this is `crates/api` work (a new route module `routes/operators.rs`, a new query in `data/queries.rs` or a new `data/operators.rs`), reusing `crates/common`'s existing `severity_rank`/`compute_sample_stats`. **No poller or aggregator change is required for Phase 1** (approach 1) — only for the persisted-rollup extension (approach 2, useful for D).

**Frontend**: `frontend/app/operators/page.tsx` (list) + optionally `frontend/app/operators/[code]/page.tsx` (detail, listing that operator's lines with per-line status — effectively a filtered `/lines`). The list page is one row/card per operator: name, worst-severity badge (`StatusBadge`), aggregate delay/cancellation figures (`formatSampleSummary`-style), a `PinToggle` (see E), reusing `AllLinesTable`'s existing operator-name resolution (`nameByCode` from `getAllTocs()`) and severity/stat-formatting helpers. This can visually mirror `LineStatusCard` (worst status + representative summary + last-updated) rather than inventing a new card shape.

**Open decision**: what counts as "an operator" for this list — every ATOC code that appears on any line's `operators` array (which includes `"TfL"` itself, plus the `LO`/`XR` TfL-adjacent codes per `AllLinesTable`'s `TFL_ADJACENT_OPERATORS`), or only "real" TOCs from the `tocs` reference table (which per `poller-tocs/src/schema.rs`'s `atoc_member`/`station_operator` flags could filter out non-operating entries)? Recommend: start from the `tocs` table (real named operators) and treat `TfL` as its own separate always-included row, matching how `AllLinesTable` already special-cases it.

## D. Historical data

**Key finding, per the task's explicit instruction**: a historical mechanism **already exists in two forms** (§0) — the raw status-change **Timeline** (`line_status_history`, short retention) and the rate **Trends** rollups (`*_stats` tables, long retention, `TrendsCharts.tsx` etc.). Neither needs to be invented from scratch for the per-line case (B). The work for D is:

1. **Extend, don't replace, `TrendsCharts.tsx`'s pattern for operators/aggregate views.** The component itself (`frontend/app/lines/[id]/history/TrendsCharts.tsx`) is already fairly generic — it takes `points: ChartPoint[]` + `granularity` + `order` + `showVolume`, with no line-specific logic baked in. **It can likely be reused as-is** for an operator's or the network's rollup trend, provided the *data* feeding it (an operator-level or network-level `LineDailyStats`-shaped series) exists.
2. **The gap is the aggregation granularity, not the charting.** Today `line_status_daily_stats`/`half_hourly_stats` etc. are all keyed by `line_id`. There is no `operator_id`-keyed or network-wide equivalent. Two options:
   - **Compute-on-read** (Phase-appropriate for launch): sum/average the existing per-line daily/half-hourly rows across every line belonging to an operator (or across all lines, for the network view) at request time. Cheap for an operator (single-digit-to-low-teens lines); for the whole network (~125 lines × up to 4 granularities × a date range) this is more rows to scan per request but still a bounded, indexed query (`line_status_daily_stats` etc. are indexed by `(line_id, day)`/`(line_id, bucket)` presumably — **not verified in this pass**, flagged as unverified). This requires new query functions in `crates/api/src/data/queries.rs` (or aggregator-side if precomputed) that `GROUP BY day`/`bucket` across a line-id set, but no new tables or migrations.
   - **Precompute** (better long-term, especially for the network-wide dashboard's history, which every visitor would otherwise trigger a full-catalogue scan for): add `operator_status_daily_stats`/`network_status_daily_stats` tables populated by the aggregator alongside its existing `record_daily_stats` cycle (`crates/aggregator/src/queries.rs`). This is a genuinely new migration + aggregator write path, sized similarly to the existing per-line stats tables.
3. **Status-change history (Timeline) for operators/network** is a harder case than rate trends: `line_status_history` is one JSONB row per line per change. An "operator's status changed" or "network status changed" timeline would need to be derived by unioning/merging the underlying lines' `line_status_history` rows and re-deriving "worst status at time T across this operator's lines" — this is materially more complex than the rate-rollup case because it requires reconstructing a merged timeline from N independent per-line event streams, not just summing counters. **Recommendation: do not build an operator/network Timeline-equivalent in Phase 1** — ship the Trends-style rate rollup (simpler, reuses existing infrastructure) for operators/network, and treat a merged status-change timeline as a stretch goal only if there's real demand, since its complexity is disproportionate to the value over "current rollup + per-line drill-down for detail."
4. **Retention**: reuse the existing `history_retention_days`/`daily_stats_retention_days`/`half_hourly_stats_retention_hours` config knobs and the existing `GET /public/history-retention` echo (`crates/api/src/routes/history_retention.rs`, `frontend/lib/types.ts`'s `HistoryRetention`) — no new retention concept needed; an operator/network view just inherits whatever ceiling its constituent per-line data already has.

**Visualization recommendation (not just options, per the task)**: reuse `TrendsCharts.tsx` verbatim for operator/network aggregate views — same rate-metric line chart + optional volume bar chart — fed by a new `operatorId`- or `networkWide`-scoped stats query. Do **not** build a new chart component or a new visual language for D; the existing granularity control (`GranularityControl.tsx`), range picker (`HistoryRangePicker.tsx`), and gap-rendering (`gapSpans`) all transfer unchanged since they operate on the generic `ChartPoint`/`TrendGranularity` shapes, not line-specific types.

## E. Homepage pinning for operators

This is the most mechanical of the five pieces because the task is explicit: reuse the existing pattern exactly, don't invent new terminology.

**Backend changes** (small, additive, mirrors `pinned_lines` exactly):
- New table `pinned_operators(user_id TEXT NOT NULL, operator_code TEXT NOT NULL, pinned_at TIMESTAMPTZ NOT NULL DEFAULT NOW(), PRIMARY KEY (user_id, operator_code))` — same shape as `pinned_lines`/`pinned_stations` in `20260710090000_preferences.sql` (updated for the `user_id` ownership column pattern from `20260828100000_add_ownership.sql`). One migration.
- `crates/api/src/data/preferences.rs`: add `list_pinned_operator_codes`, `replace_pinned_operators` — literally copy `list_pinned_line_ids`/`replace_pinned_lines` with the column renamed. No "does this operator code still exist" filtering is strictly required (operator codes are just strings tagged onto lines, unlike lines/stations there's no real "deletion" concept) — though for consistency with `filter_known_pinned_lines`'s stale-id hygiene, filtering pinned codes against the current `tocs` table + `TfL` on read would be the parallel safeguard.
- `crates/api/src/routes/preferences.rs`: add `operator_code` field to `PreferencesResponse`/read it in `get_preferences`, and a new `PUT /public/preferences/pinned-operators` route mirroring `put_pinned_lines`/`put_pinned_stations` (same unconditional whole-list replace, same validate-nothing-on-write posture).
- `frontend/lib/types.ts`'s `Preferences` interface: add `pinnedOperators: string[]`.
- `frontend/lib/api.ts`'s `getPreferences()`: update the 401 fallback to `{ pinnedLines: [], pinnedStations: [], pinnedOperators: [] }`; update `app/page.tsx`'s and `app/lines/page.tsx`'s `NO_PREFERENCES` constants identically (both currently hardcode the two-field shape and would need the third field added).
- New same-origin proxy route in `frontend/app/api/[...path]/route.ts` for `/api/preferences/pinned-operators` — **this file is a catch-all `[...path]` proxy per its name, so it likely needs zero changes** (it should already pass through arbitrary paths to the backend) — worth a quick confirm but probably not a real gap.

**Frontend changes**:
- `PinToggle` (`frontend/components/PinToggle.tsx`): widen `PinKind` from `'line' | 'station'` to `'line' | 'station' | 'operator'`, and extend its internal `key`/`endpoint` switch (currently `kind === 'line' ? 'pinnedLines' : 'pinnedStations'`) to a three-way match. This is the only component-level change needed — everything else (busy state, 401 modal, whole-list-replace semantics) is kind-agnostic already.
- `frontend/app/operators/page.tsx` (the C list page): render `<PinToggle kind="operator" id={code} initiallyPinned={pinnedSet.has(code)} needsAccountHint={viewerIsAnonymous} />` per row, same as `AllLinesTable.tsx`'s existing `<PinToggle kind="line" .../>` usage.
- `frontend/app/page.tsx`: add a third pinned section, "Your Operators", following the *exact* structural pattern of "Your Lines"/"Your Stations":
  - Fetch `preferences.pinnedOperators` (already available from the widened `getPreferences()` call already made unconditionally on this page).
  - For each pinned code, fetch/compute that operator's rollup (the same computation C's list page uses — ideally exposed as a batchable `GET /public/operators?codes=SW,VT` or reusing the single-operator detail route from C, called once per pinned operator the same way pinned-station entries are resolved today via `Promise.all` over `preferences.pinnedStations.map(...)` at `app/page.tsx:287-321`).
  - Empty state: **exactly** mirror `"You haven't pinned any lines yet. Browse all lines to pin some."` → `"You haven't pinned any operators yet. Browse all operators to pin some."`, linking to `/operators`.
  - Card per pinned operator: reuse the same single-point aggregated overview card built for C (worst-status badge + aggregate delay/cancellation summary), not a new shape — this satisfies the task's "reuse the same card for consistency" instruction directly.
  - Gate this section on `preferences.pinnedOperators.length === 0` the same fail-closed way the other two sections gate (nothing renders beyond the empty-state sentence until something is pinned) — no separate "both empty" tri-state logic is strictly required unless the "Right now" module's positioning logic (`bothPinnedSectionsEmpty`) is extended to a `allPinnedSectionsEmpty` three-way check, which would be the correct generalization once a third section exists.

**Is E small enough to fold into an earlier phase?** Yes — explicitly flagged in the phased plan below. Once C's operator rollup and `/operators` page exist, E is essentially: one migration, ~30 lines of backend route/data code duplicating an established pattern, a 3-way switch in `PinToggle`, and a homepage section copy-pasted from the existing "Your Stations" block. There is no new interaction pattern, no new UX decision, and no new infrastructure — it should ship in the **same phase as C**, not as a separate phase.

## Open questions / decisions for the user

1. **Custom lines and operator rollups.** Should a user's private custom line ever contribute to a *public* operator's aggregate rollup on `/operators`? Recommendation: no — custom lines are private and already excluded from every public aggregate (`list_lines`'s own comment on this exact question). Needs explicit confirmation since it affects the query design in C.
2. **What counts as "an operator."** The `tocs` reference table vs. the raw set of ATOC codes appearing in `operators` arrays (which includes TfL-adjacent codes like `LO`/`XR`) are two different universes. Recommend: `tocs` table rows (real named TOCs) + a single synthetic `"TfL"` row, matching `AllLinesTable`'s existing `TFL_ADJACENT_OPERATORS` folding behavior — but this is a product decision, not purely technical.
3. **Access control for the operator surfaces.** Everything else public-facing in this app (`/lines`, `/stations`, `/incidents`) is unauthenticated-readable; recommend `/operators` and its detail pages follow the same convention (public, unauthenticated), consistent with `GET /public/tocs/all` already being public. Only the *pinning* is session-gated, matching E's own requirement.
4. **Historical time ranges for operator/network views.** Per-line Trends already supports 30-min/1hr/6hr/day granularity up to the daily/half-hourly retention ceilings (a few hundred days / ~35 days respectively). Does an operator/network rollup need the *same* granularity menu, or would a simpler 24h/7d/30d preset set suffice given it's an aggregate-of-aggregates? Recommend starting with the same `HistoryRangePicker` presets for consistency, since the underlying data has the same shape either way.
5. **Precompute vs. compute-on-read for operator/network stats (D).** Whether to add `operator_status_daily_stats`/materialize the network-wide rollup, or compute both at request time from existing per-line tables, depends on real traffic/latency numbers this spec can't predict. Recommend starting compute-on-read (Phase 4) and only adding precomputed tables if the read cost becomes a problem in practice.
6. **Whether A needs its own endpoint at all**, or whether a client-side reduce over the already-fetched `GET /Line/Mode/{mode}/Status` response (as `app/page.tsx`'s `notGoodServiceSummary` already does) is sufficient forever.
