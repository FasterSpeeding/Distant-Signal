# Design: Should Distant Signal Adopt HashiCorp Vault as its Secret Store?

**Status: design proposal, not approved.** No implementation plan is
included; that is a separate, later step in this repo's process, per this
repo's own established convention (see every design under
`docs/superpowers/specs/`, none of which contain a task list).

## Goal

Investigate, with real evidence rather than a generic "another stateful
service" objection, whether adopting HashiCorp Vault as this chart's secret
store — replacing or augmenting the Helm-rendered `Secret` objects in
`charts/distant-signal/templates/*.yaml` — is a net win for this project at
its current scale (a single-maintainer, cloud-agnostic Kubernetes
deployment). The premise under test, stated by the repo owner, is that
Vault would be **less** ongoing maintenance than the status quo, not more.
This document takes that premise seriously: it inventories every real
secret this chart manages today, researches the actual 2026 mechanics of
the two dominant Kubernetes integration patterns (Agent Injector, CSI
provider) and a third one findable only by looking (Vault Secrets
Operator), investigates which Vault auth method actually fits "a pod
reading its own secret at startup," and prices out what running Vault
single-instance actually costs operationally at this deployment's scale.
The verdict below is not a foregone conclusion reached before the
investigation — see Decisions and Operational cost assessment for how it
was reached.

## Current relevant state (verified this session)

### Every `Secret`-rendering template in the chart, read in full

Three templates render `kind: Secret` objects:

- **`charts/distant-signal/templates/secret.yaml`** (171 lines, read in
  full) — the chart-wide `Secret`, rendered once per release.
- **`charts/distant-signal/templates/schedulefeed-secret.yaml`** (88 lines,
  read in full) — a second, independent `Secret` for the opt-in
  `scheduleFeed` (DTD SFTP push) subsystem.
- **`charts/distant-signal/templates/devauthentik-secret.yaml`** (31 lines,
  read in full) — a third, independent `Secret` for the opt-in local dev
  Authentik instance (`devAuthentik.enabled`), explicitly a throwaway
  dev-only IdP, not a production credential store.

No other template in `charts/distant-signal/templates/` (`grep -l "kind:
Secret"` this session) renders a `Secret`.

### The full secret inventory, counted and categorized

With every optional subsystem enabled (5 pollers, `trustConsumer`,
`scheduleFeed`, `railMcp`, `devAuthentik`), these three templates render
**40 distinct secret data keys**. Two categories, by how the value
originates — the chart's own established, explicitly-commented distinction
(`secret.yaml:36-40`, `:97-100`, `README.md:205-211`):

**Auto-generated by the chart (6 keys)** — the chart itself mints the
value and is the reason a random one is *meaningful*, using the identical
`override -> preserve-existing-via-lookup -> randAlphaNum` chain in every
case (`secret.yaml:3-23`'s own header comment names this "the single most
important correctness detail in this chart" — `lookup` reads the live
Secret back so `helm upgrade` never rotates a value the running workload
already depends on):
1. `postgres-password` (`secret.yaml:31-34`) — the bundled Postgres's own
   role password, conditional on the bundled Postgres being enabled.
2. `internal-complete-token` (`secret.yaml:81-84`) — chart-internal
   plumbing between `railMcp` and the frontend's consent bridge, conditional
   on `railMcp.enabled`.
3. `ssh_host_ed25519_key` (`schedulefeed-secret.yaml:66-68`) — this app's
   own SFTP server host key, presented to DTD's push client.
4. the DTD SFTP account password (`schedulefeed-secret.yaml:70-73`) — this
   app mints the account DTD authenticates against, the inverse of every
   RDM/Authentik credential below.
5. `AUTHENTIK_SECRET_KEY` (`devauthentik-secret.yaml:19`) — dev-only.
6. devAuthentik's own bundled-Postgres password
   (`devauthentik-secret.yaml:20`) — dev-only, no override at all.

**Never auto-generated — externally sourced, operator- or
Authentik-supplied (34 keys)** — a random value would be *meaningless*
because an external system already assigned it, or the chart's own server
identity is not what's being authenticated
(`secret.yaml:97-100`'s comment states this precisely for the RDM keys, and
it is the same reasoning repeated for every entry in this list):
- 5 × `rdm-<name>-api-key` (`secret.yaml:101-105`) — one per RDM/Rail Data
  Marketplace poller.
- 16 × `internal-oauth-username-*` / `internal-oauth-password-*`
  (`secret.yaml:41-68`) — one username+password pair per each of the 8 real
  internal callers (5 pollers, `trustConsumer`, `scheduleIngest`,
  `scheduleReference`), each an Authentik service-account app-password.
  This is the credential shape landed by
  `docs/superpowers/specs/2026-09-02-internal-service-oauth2-design.md`
  (git log: `b78d30b`, `8b660eb`, `d8150b2` — implemented and merged this
  session's own history, not still a proposal).
- `sso-client-secret` (`secret.yaml:92-95`) — Authentik's own OIDC client
  secret for human login.
- `llm-api-key` (`secret.yaml:111-113`).
- `kafka-sasl-username` / `kafka-sasl-password` (`secret.yaml:121-124`).
- `vapid-public-key` / `vapid-private-key` (`secret.yaml:135-138`) — a
  matched EC keypair, not independent random strings.
- 6 × `ldbws-*-url` / `ldbws-*-key` (`secret.yaml:150-157`) — `railMcp`'s
  own Rail Data Marketplace/LDBWS product credentials.
- the DTD SFTP public key (`schedulefeed-secret.yaml:74`) — DTD's own
  public key, when `authMethod=public-key`; the chart never sees a matching
  private key.

**Net shape**: 34 of 40 secret keys (85%) are static credentials assigned
once by an external system (Authentik, Rail Data Marketplace, a Kafka
broker operator, a self-generated VAPID keypair) that this chart only ever
stores and hands to a pod — it never mints, rotates, or otherwise manages
their lifecycle. Only 6 (15%) are values the chart itself generates, and
all 6 already use a rotation-hostile-by-design pattern (`lookup`-preserve)
specifically because rotating them silently would break something (a
running DB connection, an already-trusted SSH host key, an
already-communicated SFTP password).

### How a secret reaches a running container: `secretKeyRef` env vars, universally

`charts/distant-signal/templates/api-deployment.yaml:99-184` is
representative of every Deployment template in this chart: almost every
config value is a plain `value:` (a URL, client ID, or Authentik group
name — "public by construction," per the file's own comment at
`:140-145`), and exactly two entries use `valueFrom.secretKeyRef`:
`SSO_CLIENT_SECRET` (`:150-154`) and `VAPID_PUBLIC_KEY` (`:177-181`). Every
Rust crate's config layer (`ServiceArguments`, per the internal-service
OAuth2 design doc's own citation, `crates/*/src/data/config.rs` /
`crates/*/src/config.rs`) uses `clap`'s `#[arg(long, env)]`, reading each
value exactly once at process startup — there is no config-reload or
file-watch mechanism anywhere in this codebase. **This matters directly for
Decision 1 below**: whatever replaces or augments `secretKeyRef` has to
either keep producing a `Secret`-shaped object consumable by
`secretKeyRef`/`envFrom`, or this app needs new code (a file-watching
config layer) that does not exist today and is out of scope for a
secret-store swap alone.

### Documented friction with the status quo — real, not hypothetical

- **`README.md:203-232`** ("Generated secrets and the `lookup` limitation")
  documents, in the chart's own words, that `helm template | kubectl apply`
  is **not a supported install path** when relying on the generated
  Postgres password, because Helm's `lookup` function always returns empty
  during a dry-run/template-only render — every offline render shows a
  *different* generated password. This is a real, self-inflicted limitation
  of the lookup-preserve pattern, not a Vault-adjacent concern, but it is
  concrete evidence that the current mechanism has sharp edges.
- **`README.md:148-175`** (renaming a release) requires a manual,
  documented step: capture the live Postgres password via `kubectl get
  secret ... -o jsonpath` *before* `helm uninstall` deletes the Secret that
  holds it (`helm get values` does not capture a render-time-generated
  value), then re-supply it explicitly on the fresh `helm install`. A
  real, easy-to-miss manual step, called out in bold in the chart's own
  docs.
- **`templates/NOTES.txt:134-147`** documents that operating
  `scheduleFeed` requires a human to run `kubectl get secret ... | base64
  -d` twice after install — once for the generated SFTP password, once for
  the host key fingerprint — and communicate both to DTD's operators
  out-of-band, entirely outside any tooling this chart provides. Rotating
  either value (host key or password) is flagged in
  `schedulefeed-secret.yaml:14-20`'s own comment as something that "would
  break delivery until DTD's operators re-confirm the new one" — real
  external coordination cost that exists independent of where the value is
  *stored*.
- **`README.md:205-211` is itself stale**, a small but real documentation
  drift worth naming directly: it states "`postgres-password` ... is the
  only chart-generated secret today," which was true before the
  `railMcp`/embedded-chatbot work added `internal-complete-token`
  (`secret.yaml:81-84`, also lookup-preserve auto-generated) and before
  `scheduleFeed`/`devAuthentik` added the other four lookup-preserve
  secrets cataloged above. Not a Vault-relevant defect in itself, but real
  evidence that hand-maintained documentation about "what's generated
  where" already drifts from the actual `Secret` templates in this
  codebase — a class of problem a single source of truth (any secret
  manager, Vault included) genuinely helps with.
- **`values.yaml:24-42`** ("Shared secrets") documents the chart's own
  three-way rule for every secret value (`existingSecret` set / explicit
  value set / neither) and explicitly states the escape hatch's intended
  use: *"Use this with External Secrets Operator, Vault or SOPS."*
  **This is the single most important existing fact for this whole
  investigation**: the chart already interoperates with Vault today,
  without a single line of Vault-specific code, via the generic
  `existingSecret` + `existingSecretXKey` pattern present on every secret
  in this chart (`README.md:234-284` walks through exactly this, using
  Vault-populated Secret names as its own worked example). Whatever
  mechanism actually writes a Kubernetes `Secret` object with the right
  keys — Vault CSI provider's k8s-secret-sync, the Vault Secrets Operator,
  External Secrets Operator, or a human running `kubectl create secret`
  by hand — is already fully supported. **Adopting Vault does not require
  a single template change in this chart** if the chosen integration
  pattern lands on "produce a native `Secret` object"; it only requires
  changes if the chosen pattern is CSI-volume-mount or Agent-Injector-file
  based (see Decision 1).

### The internal-service credential rotation story is already solved — without Vault

`docs/superpowers/specs/2026-09-02-internal-service-oauth2-design.md`
(implemented this session: `git log` shows `b78d30b`, `8b660eb`, `d8150b2`
merged, plus the follow-on MCP-groups work `9499334`..`9f87acf`) redesigned
exactly the rotation-sensitive part of this chart's credential surface: the
8 internal callers' access to `api`'s `/private/*` routes now runs on
Authentik-issued, short-lived OAuth2 access tokens (client-credentials
grant), verified locally by `api` against Authentik's JWKS
(`crates/api/src/auth.rs`'s `require_internal_oauth`, per that design's
Decision 2). **This is functionally the same value proposition Vault's
dynamic-secrets capability is usually reached for** — short-lived,
centrally-revocable credentials instead of one static shared secret — and
it was achieved using the OIDC provider this project already runs
(Authentik), at zero new infrastructure. This is directly relevant to
point 5's question below: the highest-value rotation case in this chart's
entire secret surface is already closed, by a mechanism unrelated to
Vault.

## Decisions

### 1. Kubernetes integration pattern: neither the Agent Injector nor the CSI provider — a native-`Secret`-sync mechanism (Vault Secrets Operator, or the CSI provider's own k8s-secret-sync mode), *if* Vault is adopted at all

Researched directly against current (2026) `developer.hashicorp.com/vault`
docs this session, not from stale memory:

- **Vault Agent Injector** — a mutating webhook that injects an init
  container plus a long-running sidecar into every annotated pod; both
  share a shared-memory volume (`/vault/secrets`) that the sidecar keeps
  populated and refreshed. Consumption is **file-based**: the application
  is expected to read `/vault/secrets/<name>` at startup, or the operator
  writes a Consul-Template-syntax annotation to render a specific file
  format (e.g. a `.env`-shaped file, then `source`d by an entrypoint
  script before the real binary execs). **Rejected as the primary
  mechanism for this chart.** None of this app's Rust binaries read
  secrets from a file — every one of them reads `env::var()` via `clap`'s
  `#[arg(long, env)]` at a single startup instant
  (`api-deployment.yaml:99-184`, confirmed above). Adopting the Injector
  as designed would mean either (a) writing a new shell-script entrypoint
  in every one of ~10 Dockerfiles that sources a Vault-Agent-rendered file
  into the process's environment before `exec`ing the real binary — real,
  repeated plumbing across every crate's own container image, not a chart
  change — or (b) switching every crate to read secrets from files instead
  of env vars, a genuine application-code change this document is
  explicitly not scoped to design (see Explicitly out of scope). Either
  path is real, new, ongoing maintenance surface this project does not
  have today, for a pattern whose main advantage (live in-pod secret
  refresh without a pod restart) this app cannot exploit anyway, since
  every crate reads its env once at startup with no reload path.
- **Vault CSI provider** (with the Secrets Store CSI Driver) — two
  components to install (the driver plus HashiCorp's provider), a
  `SecretProviderClass` per secret set, and a CSI volume mount per pod.
  **Also file-based by default** (secrets land as files under the CSI
  mount path), with the identical file-vs-env-var mismatch as the
  Injector — **except** the CSI provider documents a **k8s-secret-sync**
  mode: `secretObjects` on the `SecretProviderClass` additionally
  replicates the mounted values into a real, native `Secret` object,
  which existing `secretKeyRef`/`envFrom` references (this chart's
  universal pattern, confirmed above) can then read completely
  unmodified. **This mode is the one CSI-provider shape that requires no
  Deployment-template change** — Vault's role is reduced to "the thing
  that populates a Secret nightly/on-`kubectl` re-mount," feeding into a
  volume this chart never queries directly.
- **Vault Secrets Operator (VSO)** — investigated this session as a third
  option not named in the task but surfaced by research: a Kubernetes
  operator (CRDs, no sidecar, no CSI driver) that watches
  `VaultStaticSecret`/`VaultDynamicSecret` custom resources and writes
  their contents **directly into native `Secret` objects**, keeping them
  in sync on a poll/renewal interval. Applications consume the result via
  the same `secretKeyRef`/`envFrom` this chart already uses everywhere —
  no sidecar, no CSI driver, no file-vs-env-var mismatch at all. **Chosen,
  if Vault is adopted**, over both the Injector and the CSI provider's
  default mode, specifically because it is the only pattern that requires
  literally zero changes to any `*-deployment.yaml` template in this
  chart: the `VaultStaticSecret`/`VaultDynamicSecret` custom resources
  would replace `secret.yaml`'s `{{- $data := dict -}}` templating as the
  thing that *produces* the chart's `Secret` objects, but every Deployment
  template's `secretKeyRef`s keep pointing at the exact same Secret/key
  names they do today.

**The real, load-bearing point this decision rests on**: because this
chart already has an `existingSecret` escape hatch on every secret
(Current relevant state, above), *none* of these three patterns needs
Vault-specific chart engineering to try — an operator running VSO or the
CSI provider's k8s-secret-sync mode today, right now, without this
document's Migration approach being implemented at all, can already point
`postgresql.auth.existingSecret`, `pollers.incidents.existingSecret`, etc.
at whatever `Secret` name VSO/CSI syncs into, and it works. What a future
chart change *would* add (Migration approach, below) is convenience —
Vault-shaped chart values instead of one big pre-populated `existingSecret`
the operator wires up by hand outside the chart's own values schema.

### 2. Auth method: Kubernetes auth (machine-to-machine, pods reading their own secrets) — Authentik-OIDC-for-Vault is a separate, non-overlapping concern for human operators only

Two genuinely different integration points, deliberately not conflated,
per the task's own framing:

- **Vault's Kubernetes auth method** (`developer.hashicorp.com/vault/docs/
  auth/kubernetes`, fetched this session): a pod presents its own
  Kubernetes ServiceAccount token to `/auth/kubernetes/login`; Vault
  validates it against the cluster's TokenReview API (a `ClusterRoleBinding`
  granting Vault's own ServiceAccount `system:auth-delegator`) and issues a
  Vault token scoped by a Vault-side role bound to that ServiceAccount +
  namespace. **This is the correct, and only sensible, auth method for
  "a service reads its own secret at pod startup"** — no human, no
  Authentik, no OIDC round trip involved; it is the direct Kubernetes-native
  analogue of the `serviceAccountName` this chart's Deployments already
  set (`_helpers.tpl`'s `distant-signal.serviceAccountName`,
  `serviceaccount.yaml`). One real, documented wrinkle: Kubernetes 1.21+
  short-lived, audience-bound projected ServiceAccount tokens require
  either `disable_iss_validation=true` on Vault's side or a properly
  configured token reviewer JWT — a real, if well-trodden, setup step, not
  a blocker.
- **Authentik-OIDC-to-Vault** (`integrations.goauthentik.io/security/
  hashicorp-vault/`, fetched directly this session per the task's
  instruction, not summarized from memory): configures Vault's **OIDC auth
  method**, entirely separate machinery from the Kubernetes auth method
  above, whose purpose is explicitly **"human operators authenticate to
  Vault via SSO"** — logging into Vault's web UI or CLI (`vault login
  -method=oidc`) using this project's already-deployed Authentik instance
  as the identity provider, with two OIDC redirect URIs
  (`.../ui/vault/auth/oidc/oidc/callback` and
  `http://localhost:8250/oidc/callback`) and an optional mapping of
  Authentik groups to Vault "external" identity groups for policy
  assignment. **This has no role in a pod fetching its own secret at
  startup** — it is a convenience for whoever administers Vault directly
  (creating/rotating KV entries, writing policies), a real and useful thing
  for a single-maintainer operator to have (one fewer credential to
  separately manage — Authentik login doubles as Vault admin login), but
  orthogonal to, not a substitute for, the Kubernetes auth method above.

**Recommendation, if Vault is adopted**: enable **both**, for their
distinct, non-overlapping purposes — Kubernetes auth for every workload
that needs to read a secret (the actual mechanism Decision 1's chosen
integration pattern authenticates through), and Authentik OIDC auth
*solely* for the human operator's own `vault login`/UI sessions when
administering Vault directly. Neither is a prerequisite for the other; a
deployment could reasonably adopt Kubernetes auth alone and administer
Vault via `root`/a local userpass account instead, at the cost of one more
credential for the operator to manage outside Authentik.

### 3. HA vs. single-instance: single-instance, Raft storage — HA has no supporting requirement in this project

No document, chart value, or design decision anywhere in this repo
establishes an uptime/HA requirement for *any* component — the bundled
Postgres is itself explicitly single-replica with "no replication, backup
or restore story (an explicit non-goal of the design)"
(`values.yaml:72-75`). Running Vault as a 3- or 5-node HA Raft cluster (the
reference architecture HashiCorp's own docs recommend for production,
sized "to allow for the failure of up to two nodes... distributed between
three availability zones") would be a strictly higher operational
commitment than every other stateful component this project already runs,
for a project with no stated HA requirement anywhere else. **A
single-instance Vault server is the only configuration consistent with how
every other piece of this deployment is already run.**

**Storage backend: Raft integrated storage, confirmed still current 2026
best practice.** HashiCorp's own docs (`docs/concepts/integrated-storage`,
`docs/configuration/storage/raft`, fetched this session) describe Raft as
the modern, built-in storage backend, requiring no separate Consul cluster
— the deprecated pre-Raft norm this task's own framing already correctly
identifies as outdated. This holds true for a single-instance deployment
too: Raft in single-node mode still gets `vault operator raft snapshot
save`/`restore` (see Operational cost assessment) as a real, working
backup mechanism, which the older `file` storage backend does not offer in
any equivalently first-class form. One real, non-obvious caveat found in
research: HashiCorp's own docs recommend **disabling `mlock()`**
specifically when using Raft, because Raft's BoltDB-backed log file does
not interact well with `mlock`'s memory-mapped-file behavior and can drive
Vault toward an out-of-memory condition once the working set exceeds
available RAM — a concrete, Raft-specific tuning note this document flags
for the memory sizing in Operational cost assessment, not a reason to
avoid Raft.

## Architecture

If adopted (see Migration approach for how this document expects the
transition to actually happen — not designed to implementation depth
here):

```
                    ┌─────────────────────────────────────────┐
                    │  Vault (single StatefulSet, 1 replica)   │
                    │  Raft integrated storage (local PVC)     │
                    │  KV v2 engine: static creds (34 keys)    │
                    │  DB engine (optional, Decision 5): the   │
                    │    ONE dynamic-secrets candidate         │
                    │    (postgres-password)                   │
                    │  Auth: kubernetes (machine) + oidc        │
                    │        (human operator, via Authentik)   │
                    └───────────────┬───────────────────────────┘
                                    │
                    ┌───────────────┴────────────────┐
                    │  Vault Secrets Operator (VSO)   │
                    │  watches VaultStaticSecret/      │
                    │  VaultDynamicSecret CRDs,         │
                    │  authenticates via k8s auth        │
                    │  (its OWN ServiceAccount, not      │
                    │  each workload's)                  │
                    └───────────────┬────────────────┘
                                    │ writes/refreshes
                                    ▼
                    a native Kubernetes Secret, SAME shape
                    secret.yaml renders today (same keys,
                    same names, via distant-signal.*SecretName
                    helpers) -- just written by VSO instead of
                    by Helm's own {{- $data := dict -}} templating
                                    │
                                    │ secretKeyRef / envFrom
                                    │ (UNCHANGED from every
                                    │  *-deployment.yaml template
                                    │  today)
                                    ▼
              api / pollers / trust-consumer / notifier / etc.
              -- exactly as they read Secrets today, no code change
```

Every internal caller's Authentik OAuth2 flow (the previous design's own
architecture) is **entirely unaffected** — Vault would store the 16
`internal-oauth-username-*`/`internal-oauth-password-*` app-password pairs
that authenticate a service *to Authentik*, the same way it stores
`llm-api-key` or an RDM key today; it plays no role in, and does not
replace, the client-credentials/JWT exchange itself.

## Migration approach (high-level, not an implementation plan)

If a future decision moves forward with adoption, the shape this document
would expect:

1. Stand up single-instance Vault (Helm chart, `standalone` topology,
   Raft storage, sized per Operational cost assessment) as an
   **independent, separately-versioned** deployment — not folded into
   `charts/distant-signal` itself, the same posture this chart already
   takes toward `devAuthentik` (an optional, clearly-separated subsystem
   with its own Secret object, not entangled with the main one).
2. Install VSO; configure Vault's Kubernetes auth method against this
   cluster; write one Vault policy per logical secret group (mirroring
   this chart's own existing `existingSecret`-toggle groupings — e.g. one
   policy per poller, one for `trustConsumer`, one for `scheduleFeed`) so
   a compromised pod's Vault token cannot read secrets belonging to a
   different service — the same least-privilege property the internal-
   service OAuth2 design already established for the `/private/*` route
   surface, applied to the secret store this time.
3. Populate Vault's KV v2 engine with the 34 externally-sourced values
   (one-time, manual — Vault does not learn an RDM API key or an Authentik
   app-password on its own; nothing about adopting Vault changes *how*
   those 34 values are obtained, only where they are stored after the
   fact) and, separately, seed the 6 chart-auto-generated values from
   their currently-live cluster `Secret` (Vault does not need to
   regenerate them — a one-time `kubectl get secret ... | base64 -d`
   import, per value, avoids any of the rotation risk `secret.yaml`'s own
   lookup-preserve pattern exists to prevent).
4. `VaultStaticSecret` CRDs replace `secret.yaml`/`schedulefeed-
   secret.yaml`/`devauthentik-secret.yaml`'s templating, each producing a
   `Secret` object under the same name/keys the chart's existing
   `_helpers.tpl` functions already resolve — no `*-deployment.yaml`
   template changes needed at all (Decision 1's whole point).
5. `charts/distant-signal`'s own `values.yaml` would gain, at most, a
   toggle to point every `existingSecret*` field at VSO-managed Secret
   names instead of requiring the operator to hand-wire ~15 separate
   `existingSecret` blocks — a convenience layer over a mechanism that
   already works without it, per Current relevant state.
6. `postgres-password` alone (Decision 5) could migrate to a
   `VaultDynamicSecret` against Vault's PostgreSQL database engine, as a
   distinct, later, optional step — not a prerequisite for anything above,
   and carrying its own separate bootstrapping dependency (Vault needs a
   superuser-capable connection to Postgres before it can manage anything,
   meaning Postgres must already be reachable and its own admin credential
   already exists somewhere, however briefly, outside Vault).

None of this is designed to implementation depth (task-by-task Helm
diffs, exact CRD YAML, rollout ordering) — that is explicitly a separate,
later planning step, contingent on the recommendation below actually being
acted on.

## Operational cost assessment (honest numbers, not hand-waving)

- **Unsealing — the single biggest, most concrete cost at this project's
  scale.** Vault's default seal is Shamir's Secret Sharing: on every
  process start (a pod restart, a node reschedule, a `kubectl rollout
  restart`, a crash), Vault requires a human to supply a quorum of unseal
  key shares before it will serve *any* request — including a brand-new
  pod's Kubernetes-auth login to fetch its own secret for the first time.
  Auto-unseal removes this, but requires a delegated KMS: HashiCorp's own
  docs (`docs/configuration/seal`, fetched this session) confirm AWS KMS,
  GCP Cloud KMS, Azure Key Vault, AliCloud KMS, OCI KMS, and the
  self-hosted **Transit** seal are all available in open-source
  (non-Enterprise) Vault — only HSM/PKCS11 auto-unseal is
  Enterprise-gated. **The real complication specific to this project**: a
  cloud KMS is not a free ride here the way it would be for a project
  already committed to one hyperscaler. This chart is deliberately
  cloud-agnostic — confirmed this session by grepping `values.yaml` and
  `README.md` for any GKE/EKS/AKS-specific wiring (none exists); the
  chart is developed and tested against `kind`/`minikube`/`k3d`
  (`README.md:321-353`) with a generic `storageClass: ""` meaning "cluster
  default." Reaching a cloud KMS for auto-unseal from a
  homelab/bare-metal/generic cluster is still *possible* (Vault only needs
  outbound network access and an IAM credential for that one cloud
  API — the rest of the cluster need not run there), but it is a genuinely
  new dependency this project has avoided everywhere else, plus one small
  new bootstrap secret (Vault's own cloud-KMS IAM credential) that has to
  live *outside* Vault, since Vault cannot unseal itself with a credential
  it would otherwise store inside itself. The Transit auto-unseal option
  is circular for a genuinely single-Vault-instance deployment (it needs a
  second, already-unsealed Vault to hold the transit key). **Net finding**:
  at this project's actual scale and actual deployment posture, the
  realistic default is Shamir manual unseal, and that is a real,
  recurring operational risk specifically *because* this is a
  single-maintainer project — an unplanned node reboot while the
  maintainer is unavailable now means every pod that needs a fresh Vault
  login (a new pod, an expired lease) is blocked until a human manually
  unseals, a failure mode this chart's current design has nowhere in it
  today (a `Secret` object, once rendered, needs no runtime dependency to
  keep serving `secretKeyRef` reads).
- **Resource footprint, single-instance, non-HA.** HashiCorp's own Helm
  chart ships with **no default `server.resources`** — production sizing
  is left entirely to the operator (confirmed this session; the chart's
  own docs say only that defaults are "tuned for an optimal getting
  started experience," not production). Community-sourced example
  configurations for a lightweight single/small Raft deployment commonly
  use requests around 250m CPU / 256Mi memory with a higher limit (e.g.
  512Mi) — modest, comparable to or smaller than this chart's own bundled
  Postgres or Redis. One Raft-specific caveat carries a real memory
  implication (Decision 3): HashiCorp recommends disabling `mlock()` with
  Raft to avoid an OOM condition once the Raft/BoltDB working set exceeds
  available RAM, meaning **memory should be sized to comfortably exceed
  the entire KV dataset's on-disk size**, not just "enough for the
  process" — for 40 secret keys' worth of small strings this is trivially
  small (kilobytes), so this caveat is a real thing to configure correctly
  but not a real resource-sizing risk at this project's actual secret
  volume.
- **Backup/restore story: real and Raft-native, at the cost of a new
  operational routine.** `vault operator raft snapshot save`/`restore`
  (confirmed this session against `developer.hashicorp.com/vault/docs/
  commands/operator/raft` and multiple corroborating sources) exports/
  restores Vault's entire state (config, metadata, KV data) to/from a
  single file — a real, working mechanism, strictly better than this
  project's own bundled Postgres, which has **no backup/restore story at
  all** today (`values.yaml:72-75`'s own "explicit non-goal" framing).
  This is a genuine point *in favor* of the premise under test: Vault's
  backup story is more mature than what this project already accepts for
  its database. The cost is a new routine that does not exist today —
  someone has to actually run `raft snapshot save` on a schedule and store
  the result somewhere durable outside the cluster (the same category of
  operational task, cron-plus-off-cluster-storage, this project has not
  yet built for Postgres either — adopting Vault does not remove the need
  to eventually build this class of tooling, it adds a second
  system needing it).
- **Upgrade cadence and licensing — a real, non-generic consideration this
  project should weigh.** Vault (Community Edition) has been
  BSL-1.1-licensed since August 2023, not MPL 2.0/OSI-approved — a
  restriction on "competing" use that is very unlikely to bind a rail
  status app, but a real fact about what "free Vault" now means,
  including that HashiCorp (now an IBM subsidiary post-2025 acquisition)
  unilaterally defines "competing." Enterprise's own release cadence
  changed in April 2026 to a twice-yearly (Spring/Fall) model under IBM's
  support framework — this does not directly bind Community Edition, but
  it signals where HashiCorp's own maintenance attention is weighted.
  **OpenBao** (a Linux-Foundation-governed, MPL-2.0-licensed fork of
  Vault 1.14, researched this session) is a genuinely real alternative:
  near-identical core functionality (KV, PKI, database dynamic secrets,
  Kubernetes auth, Raft HA) with no BSL restriction and, as of 2026,
  actively closing the Enterprise feature gap (namespaces, HSM auto-unseal
  now open-source in OpenBao specifically). **If this project adopts
  anything in this family, OpenBao is worth evaluating as a straight
  substitute for Vault Community Edition** — same integration mechanics
  (Vault's own client/API is what OpenBao implements), no license
  ambiguity, for a project with no vendor-support requirement. This
  document does not resolve which of the two to run (Open questions,
  below) but flags it as a real decision point the task's own framing did
  not anticipate.
- **New operational skill required, honestly stated.** Running Vault well
  — even single-instance — requires understanding seal/unseal state,
  policy syntax (HCL-based ACL policies), lease/TTL semantics for anything
  beyond static KV, and Raft snapshot hygiene. This is a real, new body of
  operational knowledge for a single maintainer, on top of Kubernetes,
  Helm, Postgres, and this project's own considerable application-level
  surface (Authentik, Redis, Kafka via `trustConsumer`). It is not a large
  body of knowledge relative to what this project's maintainer has already
  built (the internal-service OAuth2 redesign alone is a comparable
  amount of new-concept learning), but it is additive, not a wash.

## What specifically would get easier (point 5, answered concretely)

- **The 8 internal callers' credential rotation**: already solved, this
  session, without Vault (Current relevant state, above). Vault would add
  nothing here beyond "store the resulting Authentik app-passwords
  somewhere other than a Helm-rendered `Secret`" — real, but marginal; it
  does not touch the actual rotation mechanism (Authentik-issued
  short-lived JWTs), which Vault has no role in and could not usefully
  replace (Vault has no secrets engine for Authentik; it is not a database
  or PKI or cloud IAM system Vault knows how to speak to dynamically).
- **`postgres-password`, via Vault's PostgreSQL database secrets engine**:
  the one genuine, concrete dynamic-secrets candidate in this chart's
  entire inventory, confirmed this session against
  `developer.hashicorp.com/vault/docs/secrets/databases/postgresql`.
  Setup requires Vault holding a superuser-capable Postgres connection
  (itself a static secret, held somewhere, at least at bootstrap), a
  `CREATE ROLE ... VALID UNTIL ...` creation-statement template, and a
  TTL (commonly `1h` default / `24h` max in the docs' own examples). Real
  and working — Vault would then issue a fresh, short-lived Postgres
  credential to `api`/`aggregator` on each pod start rather than one
  static password shared for the life of the deployment. **The actual
  win is narrow**: this replaces exactly one static secret (out of 40)
  with a dynamic one, for a database this project's own chart already
  treats as single-replica with no HA/backup story — the credential's
  blast radius if leaked is already bounded by "one Postgres instance,
  one database, one role," not the kind of large, multi-tenant
  credential-sprawl problem dynamic secrets exist to solve. It is a real,
  working capability this session confirms is not over-claimed marketing
  — but it is a genuinely small, optional refinement, not a
  transformation of this chart's rotation story, and the app-side change
  needed (reading a Vault-issued, periodically-renewed credential instead
  of one static `DATABASE_URL` env var read once at startup, per the
  "no reload path" finding above) would itself require new code this
  project does not have (a live-reloading DB connection pool, or an
  accepted-cost periodic pod restart to pick up a renewed lease) — a real
  cost this document does not resolve, only names (Open questions, below).
- **Everything else (the remaining 33 static secrets)**: Vault would
  centralize storage, add an audit log of who read/wrote which secret and
  when, and (per Decision 1) avoid the value ever passing through Helm's
  own release-history `Secret` object (a real, easy-to-overlook fact: a
  Helm-rendered `Secret`'s contents are *also* persisted inside Helm's own
  `sh.helm.release.v1.<release>.v<N>` Secret, doubling the at-rest copies
  of every value this chart renders — Vault-via-VSO removes this second
  copy, since VSO writes the target `Secret` directly, outside Helm's own
  templating/release-tracking path entirely). This is real value — but it
  is the *same* value External Secrets Operator or a hand-run `kubectl
  create secret` from any other secret manager already provides, and per
  Current relevant state, this chart's `existingSecret` escape hatch
  already makes all of it available today, with zero chart engineering,
  regardless of which secret manager sits behind it.

## Explicitly out of scope

- **An implementation plan** (exact Helm/VSO YAML, CRD field values,
  rollout ordering, policy HCL text) — per this repo's convention and this
  task's own instruction, a separate, later, contingent step.
- **Switching any Rust crate from env-var config to file-based config.**
  Named in Decision 1 as the real cost of the Agent Injector/CSI-default
  pattern; not designed here, and not recommended given VSO's zero-
  application-change alternative exists.
- **A live-reloading database connection pool or any other in-app
  mechanism to consume a periodically-renewed dynamic credential** without
  a pod restart. Flagged in "What specifically would get easier" as a real
  gap if `postgres-password` migrates to the DB secrets engine; not solved
  here.
- **Choosing between HashiCorp Vault Community Edition and OpenBao.**
  Flagged in Operational cost assessment as a real, live decision this
  project should make deliberately if it proceeds, not resolved by this
  document — both share close-to-identical mechanics for everything else
  this document designs around (KV storage, Kubernetes auth, Raft,
  Postgres dynamic secrets), so nothing above is invalidated by choosing
  either.
- **A Vault backup-to-off-cluster-storage pipeline.** Named as a real,
  new operational routine this project would need to build (Operational
  cost assessment); not designed to any depth here, the same posture this
  chart already takes toward its own bundled Postgres having no such
  pipeline.
- **Defining Vault ACL policies, Kubernetes auth roles, or the Authentik
  OIDC application/provider for human Vault admin login** in concrete
  detail — Decision 2/Migration approach name the shape; provisioning them
  is deployment-time/operator work, the same posture every other design
  document in this repo takes toward Authentik-side provisioning (e.g. the
  internal-service OAuth2 design's own "Explicitly out of scope").
- **HA Vault** — explicitly rejected in Decision 3 as unsupported by any
  requirement this project has established anywhere.
- **Migrating `scheduleFeed`'s SSH host key or SFTP password rotation
  process.** Vault does not remove the external-coordination cost with
  DTD documented in `schedulefeed-secret.yaml:14-20`/`NOTES.txt:134-147` —
  whoever holds the value still has to tell DTD's operators about a
  rotation out-of-band, regardless of where the value is stored.

## Open questions/risks

1. **Whether the maintainer already has, or is willing to provision, a
   cloud KMS credential for auto-unseal** — the single fact that most
   changes this document's own operational-cost conclusion. With
   auto-unseal genuinely wired up, the unsealing cost (this document's
   single largest concrete objection) shrinks dramatically; without it,
   Shamir manual unseal is a real, recurring single-maintainer risk. Not
   resolved here — an operator-environment fact this document cannot
   assert either way.
2. **HashiCorp Vault Community Edition vs. OpenBao** — flagged above as a
   real, live choice, not resolved. Worth a short, dedicated evaluation
   before any implementation plan is written, given the mechanics this
   document designs around are shared by both.
3. **Whether the `postgres-password` -> DB-secrets-engine migration
   (the one genuine dynamic-secrets win identified) is worth its own
   real cost** — no live-reload mechanism exists in `crates/api`/
   `crates/aggregator` today, and building one is real, new application
   code. This document does not resolve whether that cost is worth a
   single static password becoming dynamic for a single-replica,
   no-HA database whose leak blast radius is already small.
4. **Where Vault's own bootstrap secrets live** (the initial root token,
   the Shamir unseal key shares or the cloud-KMS IAM credential, and — if
   the DB secrets engine is adopted — the superuser-capable Postgres
   connection string Vault itself needs). Adopting Vault does not
   eliminate "a secret that has to exist somewhere outside any secret
   manager" — it relocates that smallest, most sensitive tier of secret
   from "40 chart-rendered values" to "a handful of Vault-bootstrap
   values," which is a real reduction in surface area, but not a
   reduction to zero. Not designed to any operational depth here.
5. **Whether VSO's own authentication to Vault (Decision 1's chosen
   pattern) should use a distinct Kubernetes-auth role per logical secret
   group, or one shared role for the whole operator's convenience** — a
   real least-privilege question (Migration approach step 2 suggests
   per-group, mirroring the existing `existingSecret` groupings) not
   resolved to implementation depth here.
6. **This document's own confidence in third-party research (WebFetch
   summaries, not primary-source verification against a real running
   Vault instance) for the more granular mechanics** — e.g. the exact
   default lease durations Vault's PostgreSQL engine ships with, or the
   precise behavior of `disable_iss_validation` against this project's
   actual Kubernetes distribution's token issuer. Corroborated across
   HashiCorp's own current docs this session, but not verified against a
   live Vault instance in this repo's own dev environment the way, e.g.,
   `genPrivateKey "ed25519"`'s actual output was verified in the
   `scheduleFeed` design's own implementation. Flagged as a real
   implementation-time verification step if this document's
   recommendation is acted on.

## Recommendation

**Do not stand up a new, dedicated Vault (or OpenBao) instance for this
project at its current scale.** The evidence gathered above does not
support the premise that it would be less ongoing maintenance than the
status quo, for three concrete, specific reasons — not a generic "another
stateful service" objection:

1. **The highest-value rotation problem this chart had — the 8 internal
   callers' shared, unrevocable credential — is already solved**, this
   session, by the Authentik OAuth2 redesign, at zero new infrastructure.
   Vault's dynamic-secrets story, the strongest concrete argument for
   adopting it, has exactly one remaining real candidate in this chart's
   entire 40-key inventory (`postgres-password`), for a single-replica
   database this project's own chart already accepts has no HA/backup
   story — a narrow, optional win, not a transformation.
2. **The other 33 secrets are static, externally-assigned values Vault
   cannot dynamically generate for** (no Vault secrets engine speaks
   Rail Data Marketplace, Authentik app-passwords, or a VAPID keypair) —
   Vault's benefit there is centralized storage and an audit log, real
   but not exclusive to Vault: this chart's own `existingSecret` escape
   hatch already gets that same benefit from any secret manager, Vault
   included, today, with zero chart engineering.
3. **The one concrete, sized, honestly-assessed new cost — unsealing —
   is a real, recurring single-maintainer operational risk specifically
   because this project is deliberately cloud-agnostic** (no
   hyperscaler-managed KMS is a free, already-present dependency the way
   it would be for a project already committed to one cloud), and the
   other new costs (a second backup routine to build, a new operational
   skill set, a license/fork decision between Vault CE and OpenBao) are
   real and additive, not imaginary.

**The qualified exception**: if this project's maintainer already runs, or
plans to run, Vault (or OpenBao) for reasons independent of this project
— with auto-unseal already solved for those other reasons — then pointing
this chart's existing `existingSecret` fields at that already-running
instance (via VSO or the CSI provider's k8s-secret-sync mode) is a low-
cost, reasonable thing to do, and this document's Architecture/Migration
approach sections describe what that would look like. **Standing up Vault
newly, for this project alone, is not justified by the evidence gathered
here.**
