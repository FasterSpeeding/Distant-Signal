# Per-Service Metrics Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give every one of this app's eight Rust binaries (`api`,
`aggregator`, `enricher`, and the five pollers) a scrapeable Prometheus
`/metrics` endpoint exposing the operational signals this repo's own design
docs already treat as important — poll-cycle health, LLM call latency/
failure, Redis Streams consumer lag, TfL's retry/rate-limit behavior — and
wire the Helm chart's `PodMonitor`/annotation scrape targets the chart's own
design doc explicitly deferred, per
`docs/superpowers/specs/2026-08-29-metrics-design.md`.

**Architecture:** Every service exposes a pull-based `/metrics` endpoint via
the `metrics` facade + `metrics-exporter-prometheus` exporter — `api`
composes `axum-prometheus`'s middleware onto its existing `axum` router and
listener (cheapest case, no new port); the other seven binaries
(`aggregator`, `enricher`, five pollers) call a new
`crates/common::metrics::install(port)` helper once at startup, which spins
up `metrics-exporter-prometheus`'s own embedded `hyper` listener on a new,
configurable port (default `9091`) — no `axum` dependency added to any of
those six crates. Every hand-instrumented metric name goes through a second
new helper, `crates/common::metrics::metric_name`, which applies a shared
`nr_status_` prefix so hand-written metrics from six different crates can
never collide with each other or with `metrics-exporter-prometheus`'s own
process-level defaults. The Helm chart's last task wires a `PodMonitor`
(gated `podMonitor.enabled=false`, mirroring `networkPolicy.enabled`'s
existing default-off posture) plus unconditional `prometheus.io/scrape`
pod annotations as a CRD-free fallback, once every workload actually has
something listening on its metrics port to scrape.

**Tech Stack:** Rust (`metrics` 0.24, `metrics-exporter-prometheus` 0.18,
`axum-prometheus` 0.10 — new dependencies, versions as confirmed by the
design doc's crate-landscape research pass), `crates/common` (new
`metrics` module), all eight existing crates' `main.rs`/`config.rs`, Helm
(`charts/nr-status`) — a new `PodMonitor` template plus modifications to
every Deployment template and `networkpolicy.yaml`.

**Spec:** `docs/superpowers/specs/2026-08-29-metrics-design.md` — read in
full before starting; this plan does not restate its research (Prometheus
pull vs. OpenTelemetry push, the crate-landscape comparison, `PodMonitor` vs
`ServiceMonitor`), only its resulting decisions. Also read
`docs/superpowers/specs/2026-08-18-helm-chart-design.md` for the chart
conventions Task 10 must match.

## Sequencing note: real current code shape vs. the design doc

The design doc was written before this repo's SSO work
(`docs/superpowers/plans/2026-08-28-user-accounts-sso.md`) landed — it is
confirmed landed as of this plan (`git log --oneline -- crates/api/src/auth`
shows `crates/api/src/auth/oidc.rs` and its migrations already committed,
ancestors of this plan's base commit). That matters here for one concrete
reason: **`crates/api/Cargo.toml` now pins `reqwest = "0.12"` deliberately**,
with a comment explaining `oauth2`/`openidconnect` require it (a `cargo add
reqwest@0.13` for anything unrelated would split `api` across two
incompatible `reqwest::Client` types). This plan's `axum-prometheus`
dependency (Task 2) does not touch `reqwest` at all, so there is no
conflict — but it's worth knowing this pin exists before touching
`crates/api/Cargo.toml` for any reason. Everything else this plan touches
(`crates/aggregator/src/main.rs`'s `run_cycle` at lines 55-87,
`crates/enricher/src/main.rs`'s three-call `process_incident` at lines
228-250 and `MismatchTracker` at lines 121-156, `crates/poller-tfl/src/
main.rs`'s `fetch_json` at lines 241-265, `charts/nr-status/templates/
networkpolicy.yaml`'s "exposes no listener" comments at lines 88, 169, 185)
was re-read against the actual files while writing this plan and matches
the design doc's own citations closely — line numbers drifted by at most a
few lines, not the file shapes. One thing the design doc's Architecture
section undersold: `enricher`'s `main.rs` now runs *three* independent
background loops, not two — a stream consumer loop, an hourly `sweep_loop`,
and a `reclaim_loop` for stale pending Streams entries (the "PEL reclaim"
the design doc's Problem section already named) — Task 9 accounts for all
three.

## Global Constraints

- **Prometheus pull model via `metrics` + `metrics-exporter-prometheus`,
  not OpenTelemetry.** `axum-prometheus` for `api`'s HTTP layer specifically;
  hand-written `counter!`/`histogram!`/`gauge!` calls everywhere else. Not
  relitigated here — see the design doc's Research sections.
- **`crates/common::metrics` is the one shared install point**, mirroring
  `crates/common::ingest`'s existing precedent (its own module doc: "the
  one place that changes if either... ever needs to"). It exposes exactly
  two functions: `metric_name(suffix: &str) -> String` (prepends the shared
  `nr_status_` prefix — pure, unit-tested) and `install(port: u16) ->
  anyhow::Result<()>` (starts the embedded exporter listener — not
  unit-tested, see the testing-convention bullet below). `api` does **not**
  call `install` — it already has a listener to attach `axum-prometheus`'s
  middleware to instead (Task 2).
- **Port convention.** `api` reuses its existing HTTP port
  (`api.service.port`, default `8080`) — `/metrics` is just another route
  on the router it already serves. The other six workloads
  (`aggregator`, `enricher`, five pollers) each get a new `METRICS_PORT`
  env var / `--metrics-port` CLI flag, default `9091` — distinct from
  `8080`/`3000`/`5432`/`6379`, and safe to reuse across all six Deployments
  since each runs in its own pod's network namespace (no collision).
- **Metric naming.** Every hand-written metric name is built through
  `common::metrics::metric_name`, giving every one the shared `nr_status_`
  prefix (e.g. `nr_status_poller_cycle_total`). The one exception is `api`'s
  HTTP-layer metrics, which keep whatever prefix `axum-prometheus` itself
  applies by default — the design doc's own metric table frames that row as
  "via axum-prometheus defaults," not as a `common::metrics::metric_name`
  call site.
- **Cardinality discipline — no per-line/per-station labels anywhere,
  full stop.** The `poller` label is a fixed set of five known strings
  (`incidents`, `stations`, `tocs`, `ldbws`, `tfl`), not user data. The
  poll-cycle `result` label stays `success`/`failure` only — no attempt to
  taxonomize failure *reasons* into a label (design doc Open Question 5);
  the full error stays in the paired `tracing::error!` log line, unchanged.
  `enricher`'s LLM-call `outcome` label is `success`/`error` only in this
  plan (not the design table's illustrative `success`/`error`/`timeout` —
  see Task 9's note on why a `timeout` distinction isn't currently
  implementable without a typed error `LlmClient` doesn't have today).
- **`PodMonitor` (Prometheus Operator CRD), not `ServiceMonitor` — no new
  Kubernetes `Service` objects for any of the six workloads that don't
  already have one.** Gated `metrics.podMonitor.enabled=false` by default,
  mirroring `networkPolicy.enabled`'s existing default-off reasoning (a
  silently-unrenderable CRD given the operator isn't installed is worse
  than an explicit opt-in). `prometheus.io/scrape`/`port`/`path` pod
  annotations render unconditionally whenever `metrics.enabled` is `true`
  (default `true`) as the CRD-free fallback — this is the one piece of the
  metrics feature that stays "on" by default, since it's just annotations,
  costs nothing if nothing reads them, and keeps the "works with no
  operator prerequisites" posture intact even for metrics specifically.
- **No `/metrics` authentication.** Per the design doc's Open Question 3
  resolution: cluster-internal only (no Ingress route, ever), NetworkPolicy-
  gated when NetworkPolicy is enabled (Task 10) — no bearer token, unlike
  `/private/*`.
- **Explicitly out of scope for this plan** (per the design doc's
  Non-goals, restated here so no task tries to sneak them in): per-line/
  per-station labeled metrics, `sqlx` query-level histograms, dashboards or
  `PrometheusRule` alerting, a bundled Prometheus/Grafana stack, the
  `push-gateway` feature of `metrics-exporter-prometheus`, and the
  `frontend` (Next.js) service.
- **Testing convention for metrics.** Every task in this plan that adds a
  hand-written `counter!`/`histogram!`/`gauge!` call site is verified by a
  scripted `curl localhost:<port>/metrics | grep nr_status_...` check in
  that task's own verification step, **not** a Rust unit test, for a
  concrete, reproducible reason: `metrics-exporter-prometheus`'s
  `PrometheusBuilder::install` sets a process-global recorder exactly once
  per process — a second call anywhere in the same test binary either
  errors or silently does nothing depending on the exact API (confirm which
  at implementation time), and Rust's default test runner executes `#[test]`
  functions from the same binary concurrently on separate threads, so "spin
  up the exporter in a test and assert a counter incremented" would be
  racing every *other* test in that binary over one shared piece of global
  state — a flaky, not-actually-isolated test masquerading as a clean one.
  The one piece of new logic that genuinely is pure and unit-testable is
  `common::metrics::metric_name` itself (Task 1) — TDD applies there in the
  normal way. This mirrors the honesty this repo's other plans already
  apply to similar untestable-in-isolation surfaces (see the SSO plan's
  reasoning for not hand-rolling a fake-signed-JWT IdP to test the OIDC
  exchange itself).
- **New dependencies introduced by this plan:** `metrics-exporter-
  prometheus` (in `crates/common` only — it owns `install`), `metrics` (in
  `crates/aggregator`, `crates/enricher`, and all five poller crates — each
  needs its own direct dependency to call the `counter!`/`histogram!`/
  `gauge!` macros), `axum-prometheus` (in `crates/api` only). No new
  dev-dependencies.
- **No new crate.** Unlike the incident-NLP-extraction and SSO plans, this
  one adds no new binary or library crate — every change lives inside the
  eight crates that already exist, plus the Helm chart.

```rust
//! Shared Prometheus metrics installer for the six binaries that have no
//! HTTP server of their own today (`aggregator`, `enricher`, and the five
//! pollers) -- mirrors `crates/common::ingest`'s precedent of being "the
//! one place that changes" for boilerplate every one of those binaries
//! would otherwise repeat (`crates/common/src/ingest.rs`'s own module doc).
//! `api` does NOT call `install` (see
//! docs/superpowers/plans/2026-08-29-metrics.md's Task 2): it already has
//! an axum listener to attach `axum-prometheus`'s middleware to instead,
//! and composes the same underlying `metrics` facade through that crate.
//!
//! See docs/superpowers/specs/2026-08-29-metrics-design.md's Architecture
//! section for the full reasoning behind this split.

/// Every metric this app emits by hand is prefixed `nr_status_`, so it can
/// never collide with `metrics-exporter-prometheus`'s own process-level
/// defaults (e.g. `process_cpu_seconds_total`) or a future metric from an
/// unrelated process sharing the same Prometheus instance. Callers build a
/// metric's full name through this function rather than hand-writing the
/// prefix at each of the (many) call sites across six crates, so the one
/// place that changes if the prefix itself ever does is this function, not
/// every call site.
pub fn metric_name(suffix: &str) -> String {
    format!("nr_status_{suffix}")
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn metric_name_adds_the_shared_prefix() {
        assert_eq!(metric_name("poller_cycle_total"), "nr_status_poller_cycle_total");
    }

    #[test]
    fn metric_name_does_not_detect_or_strip_an_already_prefixed_suffix() {
        // Documents current behavior rather than testing a real
        // requirement: metric_name always prepends, it never inspects its
        // input. Callers are responsible for passing a bare suffix (e.g.
        // "poller_cycle_total", not "nr_status_poller_cycle_total").
        assert_eq!(
            metric_name("nr_status_poller_cycle_total"),
            "nr_status_nr_status_poller_cycle_total"
        );
    }
}
```

```rust
use std::net::{IpAddr, Ipv4Addr, SocketAddr};

use anyhow::{Context, Result};
use metrics_exporter_prometheus::PrometheusBuilder;

/// Installs the process-global Prometheus recorder and starts its embedded
/// HTTP listener on `0.0.0.0:<port>`, serving `/metrics` in Prometheus text
/// exposition format. Must be called exactly once, near the top of `main`,
/// before any `counter!`/`histogram!`/`gauge!` call and before the caller's
/// real work begins -- `metrics`'s macros are silent no-ops against no
/// installed recorder, dropping every observation rather than erroring, if
/// this hasn't run yet.
///
/// No `axum` dependency: `metrics-exporter-prometheus`'s
/// `with_http_listener` spins up its own minimal `hyper`-based listener, so
/// this doesn't pull a web framework into six crates that have never
/// needed one -- confirmed against the crate's docs.rs page as part of
/// this feature's design pass
/// (docs/superpowers/specs/2026-08-29-metrics-design.md).
///
/// Note: the exact builder method names below
/// (`PrometheusBuilder::with_http_listener`, `.install()`) match
/// `metrics-exporter-prometheus` 0.18's documented usage as of the design
/// doc's research pass, but this plan was written without the ability to
/// compile-check against the crate directly -- confirm against `cargo doc
/// -p metrics-exporter-prometheus --open` while implementing this step.
pub fn install(port: u16) -> Result<()> {
    let addr = SocketAddr::new(IpAddr::V4(Ipv4Addr::UNSPECIFIED), port);
    PrometheusBuilder::new()
        .with_http_listener(addr)
        .install()
        .context("failed to install the Prometheus metrics exporter")?;
    Ok(())
}
```

Add a comment to the bottom of the `#[cfg(test)] mod tests` block (not a
test itself — see this plan's Global Constraints on why):

```rust
    // Verified instead by Task 1 Step 7's manual curl check below, and
    // implicitly by every downstream task's own manual verification step,
    // each of which depends on `install` having actually started a
    // listener.
```

```rust
        .build_pair();

        .merge(routes::line_status::router())
```

```rust
/// One authenticated GET against TfL, with this poller's shared status
/// checking, in-cycle backoff, and outcome metric. Every TfL call goes
/// through here: a 429 or a 5xx has a body too, and handing that body to a
/// parser produces a confusing serde error in place of the real cause.
///
/// `what` names the call in errors, logs, and the `nr_status_tfl_fetch_total`
/// metric's `what` label (e.g. `"line-status"`).
async fn fetch_json(client: &Client, url: &str, config: &Config, what: &str) -> anyhow::Result<String> {
    let mut attempt = 0;
    // Tracks the status code of the most recent retryable failure, if any
    // -- this is what distinguishes a same-cycle "succeeded on the first
    // try" outcome from "succeeded after backing off from a 429/5xx",
    // which the plain success/failure result of the call alone can't tell
    // apart. See docs/superpowers/specs/2026-08-29-metrics-design.md's v1
    // scope item 3.
    let mut retried_status: Option<StatusCode> = None;
    loop {
        let response = client
            .get(url)
            .header(TFL_AUTH_HEADER_NAME, &config.tfl_app_key)
            .send()
            .await?;
        let status = response.status();

        if status.is_success() {
            let outcome = match retried_status {
                None => "success",
                Some(s) if s == StatusCode::TOO_MANY_REQUESTS => "retried_429",
                Some(_) => "retried_5xx",
            };
            metrics::counter!(
                common::metrics::metric_name("tfl_fetch_total"),
                "what" => what.to_string(),
                "outcome" => outcome
            )
            .increment(1);
            return Ok(response.text().await?);
        }

        attempt += 1;
        if attempt >= MAX_ATTEMPTS || !should_retry(status) {
            metrics::counter!(
                common::metrics::metric_name("tfl_fetch_total"),
                "what" => what.to_string(),
                "outcome" => "exhausted"
            )
            .increment(1);
            let body = response.text().await.unwrap_or_default();
            anyhow::bail!("TfL {what} fetch failed: {status} {body}");
        }

        retried_status = Some(status);
        let delay = retry_delay(attempt);
        tracing::warn!(%status, attempt, delay_secs = delay.as_secs(), "TfL {what} fetch failed; retrying");
        tokio::time::sleep(delay).await;
    }
}
```

Note: this covers the retryable-failure path (`should_retry` returning
`true`, i.e. 429/5xx). A non-retryable client error (`is_err` from
`should_retry` returning `false`, e.g. a 401 from a bad key) also hits the
`attempt >= MAX_ATTEMPTS || !should_retry(status)` branch on its very first
attempt and is recorded as `outcome = "exhausted"` — not a separate
`outcome` value. The design doc's proposed outcome set
(`success`/`retried_429`/`retried_5xx`/`exhausted`) doesn't distinguish
"gave up after retries" from "failed immediately, non-retryable" either, so
this matches the design as written; a reviewer wanting that split would add
a fifth outcome value here.

Also add `use metrics;` alongside the file's existing imports if not
already present via a bare `metrics::` path (the snippet above uses fully
qualified `metrics::counter!` so no import is strictly required, matching
this crate's existing style of minimal top-level `use` statements for
macros).

In `crates/enricher/src/stream.rs`, add:

```rust
/// Redis 7's `XINFO GROUPS` reply is an array of per-group entries, each a
/// flat array of alternating field name/value pairs. This pulls out the
/// `enricher` group's own `lag` field -- how many stream entries the
/// group's last-delivered id is behind the stream's tail. `None` if the
/// group doesn't exist yet (a fresh stream before `ensure_group` has ever
/// run, or immediately after a Redis restart wiped it -- see `main.rs`'s
/// own NOGROUP self-heal comment for that exact scenario) or if this Redis
/// server predates the `lag` field (added in Redis 7.0; `docker-
/// compose.yml` already pins `redis:7`, so this should always be present
/// in this app's own deployments, but a self-managed external Redis might
/// not be).
///
/// Note: the exact `redis` crate 0.27 `Value` variant name used for a
/// nested array reply (`Value::Array` below) should be confirmed against
/// `cargo doc -p redis --open` at implementation time -- some `redis` crate
/// versions name this variant `Value::Bulk` instead.
pub async fn group_lag(conn: &mut ConnectionManager) -> anyhow::Result<Option<i64>> {
    let reply: Vec<redis::Value> = redis::cmd("XINFO").arg("GROUPS").arg(STREAM).query_async(conn).await?;

    for group in reply {
        let redis::Value::Array(fields) = group else { continue };
        let mut name: Option<String> = None;
        let mut lag: Option<i64> = None;
        let mut iter = fields.into_iter();
        while let (Some(key), Some(value)) = (iter.next(), iter.next()) {
            let key: String = redis::from_redis_value(&key)?;
            match key.as_str() {
                "name" => name = redis::from_redis_value(&value).ok(),
                "lag" => lag = redis::from_redis_value(&value).ok(),
                _ => {}
            }
        }
        if name.as_deref() == Some(GROUP) {
            return Ok(lag);
        }
    }
    Ok(None)
}
```
