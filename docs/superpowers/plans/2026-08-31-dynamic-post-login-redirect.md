# Dynamic Post-Login Redirect Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** After a successful SSO sign-in, land the browser back on the page the user was actually on when they clicked "Log in" — path plus query string — instead of always redirecting to the single, operator-configured `sso_post_login_redirect_url`. Today `GET /auth/callback` (`crates/api/src/routes/auth.rs:146`) unconditionally does `Redirect::temporary(&app.config.sso_post_login_redirect_url)`; this was a deliberate v1 scope simplification (`crates/api/src/data/config.rs:101-104`, `docs/superpowers/plans/2026-08-28-user-accounts-sso.md:140-144`) that this plan closes.

**Architecture:** One new nullable column on the existing `oidc_login_state` table carries the validated return path through the OAuth round trip — no second mechanism, and the OAuth `state` parameter itself is untouched. Capture is client-side (a new `LoginLink` component reading `usePathname()`/`useSearchParams()`), validation is server-side (a same-origin, relative-path-only check using the `url` crate), and any missing or invalid value silently falls back to today's static `sso_post_login_redirect_url` — never a user-visible error.

```
frontend/components/LoginLink.tsx   NEW -- 'use client', wraps TextLink,
                                       appends ?return_to=<path+query>
  ▲ embedded at 7 call sites (AuthStatus, TicketPanel, CustomLineForm,
    DeleteLineButton, TicketEntryForm, TrackTrainForm, PinToggle)
        │ GET /api/auth/login?return_to=... (proxy forwards query as-is,
        │ no proxy change needed)
        ▼
crates/api/src/routes/auth.rs::login()      -- extract, validate, store
crates/api/src/auth.rs::validate_return_to  -- NEW, same-origin relative-path check
crates/api/src/data/users.rs                -- LoginState.return_to,
                                                insert_login_state(..., return_to),
                                                consume_login_state RETURNING return_to
crates/api/migrations/20260831090000_login_state_return_to.sql  NEW
                                                ALTER TABLE oidc_login_state
                                                ADD COLUMN return_to TEXT
        │ (round-trips through the IdP untouched -- state param unchanged)
        ▼
crates/api/src/routes/auth.rs::callback()   -- re-validate, redirect-or-fallback
```

**Tech Stack:** Rust (axum, sqlx, the `url` crate already pulled in transitively via `openidconnect::url` — confirmed already imported at `crates/api/src/auth/oidc.rs:10`, so no `Cargo.toml` change is needed anywhere in this plan) for the backend tasks; Next.js App Router + TypeScript + Mantine v9, Vitest + `@testing-library/react` + this repo's `renderWithMantine` helper (`frontend/test/render.tsx`) for the frontend tasks.

**Spec:** `docs/superpowers/specs/2026-08-31-dynamic-post-login-redirect-design.md` — read in full before starting; this plan does not restate its research, only carries its decisions into concrete tasks. Cross-references below to spec sections refer to that document.

**Status note (confirmed by direct inspection while writing this plan, 2026-09-01):** `crates/api/src/routes/auth.rs` has no tests today (`grep -n "mod tests|#\[test\]"` returns nothing in that file) — Task 4/5 introduce the first ones. `crates/api/src/auth.rs` already has one `#[cfg(test)] mod tests { use super::*; ... }` block at the bottom (covering `constant_time_eq`, `parse_cookie`, `set_cookie_header`, `clear_cookie_header`, `hash_session_token`, `generate_session_token`) — Task 2's `validate_return_to` tests are added to that same module, not a new one. No page in this frontend currently calls `usePathname()`/`useSearchParams()` anywhere (`grep -rln "usePathname|useSearchParams"` across `frontend/`, excluding `node_modules`/`.next`, returns nothing) — `LoginLink` is this codebase's first use of either hook, so Task 7's test-file updates are genuinely new test surface, not an extension of an established mocking pattern for these two hooks specifically (the `useRouter` mocking pattern they'll sit alongside *is* already established, at all 5 of the 7 call sites that are Client Components).

## Global Constraints

- **The OAuth `state` parameter is not touched anywhere in this plan.** It stays a bare `CsrfToken::new_random()`, generated by `app.oidc.authorize_url()` and compared byte-for-byte in `callback()`, exactly as today. This is a deliberate, researched decision in the spec (RFC 9700's tampering warning against packing application state into `state`) — no task in this plan reconsiders it.
- **`validate_return_to` must be implemented exactly as specified** in the design doc's Design → Validation section (Task 2 below reproduces it in full) — it is this feature's entire open-redirect defense. Do not simplify, reorder its checks, or skip the authoritative `url`-crate-based recheck in favor of the prefix checks alone.
- **No new Cargo dependency.** `openidconnect::url::Url` is already imported and used in `crates/api/src/auth/oidc.rs:10` — `validate_return_to` uses that same re-export (`openidconnect::url::Url`), not a fresh `use url::...` requiring a new `Cargo.toml` line.
- **Fallback is always silent.** A missing `return_to`, or one that fails validation at either `login()`-time or `callback()`-time, must degrade to `app.config.sso_post_login_redirect_url` — never a `4xx`/`5xx` response or user-visible error on an otherwise-successful sign-in. No task may add an error branch for this case.
- **No redirect-loop guard is implemented in this plan.** The spec flags, but explicitly does not resolve, that `validate_return_to` as specified accepts `/api/auth/login` or `/api/auth/callback` themselves as "valid" (they're same-origin absolute-path references, which is all the check verifies). Task 2's own test suite includes an explicit test asserting this *current* (accepted, not rejected) behavior, specifically so a future implementer who adds the guard has a test that will visibly fail and force them to update it — not a silent gap. Do not add the guard as part of this plan.
- **URL fragments (`#...`) can never be captured.** A fragment is never sent to the server on any HTTP request (a property of the URL/HTTP specs, not a bug in this design) — `LoginLink` has no way to include one, and no task in this plan should attempt to work around this.
- **The `2048`-byte cap on `return_to` (Task 2) is the spec's own placeholder value, not measured against this app's real longest route.** Implement it as specified; do not research or substitute a different number as part of this plan.
- **`frontend/components/TextLink.tsx` itself is not modified.** It deliberately stays a non-Client Component (most of its call sites are Server Components) — `LoginLink` wraps it rather than adding hooks to it directly.
- **No change to `app/api/[...path]/route.ts` (the Next.js proxy).** It already forwards the incoming query string verbatim (`` `${API_BASE_URL}${resolveTargetPath(path)}${req.nextUrl.search}` ``), so `return_to` reaches the backend unmodified with zero proxy changes. No task in this plan touches that file.
- **`sso_redirect_url`, `cookie_secure`, and the `Secure`-cookie derivation are out of scope** — untouched by every task in this plan, per the spec's own Non-goals.
- **Testing convention:** Rust `#[cfg(test)] mod tests` colocated in the same file, matching `crates/api/src/auth.rs`'s existing precedent (Task 2) and `train_tracking.rs`'s (Task 3/4/5, new modules where none existed). Frontend: colocated `*.test.tsx`, `@testing-library/react`, `renderWithMantine`, Vitest (`npm test` from `frontend/`). Every frontend task's verification step runs `npm test` and `npm run build` (both from `frontend/`) and requires both to pass with no new failures. Every backend task's verification step runs `cargo test -p api` and requires it to pass with no new failures.

- [ ] **Step 1: Add the function**

Add to `crates/api/src/auth.rs`, near `parse_cookie`/`set_cookie_header`:

```rust
/// Accepts only a same-origin, absolute-path, relative URL reference --
/// rejects anything that could make `Redirect::temporary` send a
/// just-authenticated, trusting browser somewhere off-site (open
/// redirect / post-login phishing). Called twice per login: once in
/// `routes::auth::login` (validate before persisting to
/// `oidc_login_state`) and once in `routes::auth::callback` (validate
/// again before using the persisted value) -- see that module for both
/// call sites.
pub fn validate_return_to(raw: &str) -> Option<String> {
    const MAX_LEN: usize = 2048;
    if raw.is_empty() || raw.len() > MAX_LEN {
        return None;
    }
    // Header-injection guard, and a defense against browsers that strip
    // or reinterpret stray control characters (tabs, NULs) during URL
    // normalization in ways this function shouldn't have to model.
    if raw.chars().any(|c| c.is_control()) {
        return None;
    }
    // Some browsers normalize a leading `/\` (or backslashes generally)
    // into `//` during navigation -- i.e. into a protocol-relative URL.
    // Rejecting `\` anywhere sidesteps needing to reason about exactly
    // which browsers do this and how.
    if raw.contains('\\') {
        return None;
    }
    // Must be an absolute-path reference: exactly one leading '/', not
    // '//...' (protocol-relative -- a browser resolves this to
    // `https://<attacker-controlled-host>/...`) and not a scheme
    // (`javascript:`, `https:`, etc., which `starts_with('/')` already
    // excludes on its own, but is worth stating as intent).
    if !raw.starts_with('/') || raw.starts_with("//") {
        return None;
    }
    // Authoritative check, not just belt-and-braces: resolve `raw`
    // against a fixed, arbitrary dummy origin using the same URL parser
    // this crate already depends on (`openidconnect::url`, i.e. the
    // `url` crate -- a WHATWG URL Standard implementation, the same
    // parsing algorithm real browsers use). If the parsed result's
    // scheme/host ever differ from the dummy origin, `raw` smuggled a
    // scheme or host past the prefix checks above through some
    // normalization quirk those checks didn't anticipate -- reject
    // rather than trust the prefix checks alone.
    let base = openidconnect::url::Url::parse("http://return-to.invalid").ok()?;
    let joined = base.join(raw).ok()?;
    if joined.scheme() != "http" || joined.host_str() != Some("return-to.invalid") {
        return None;
    }
    Some(raw.to_string())
}
```

This is a verbatim implementation of the spec's Design → Validation section — do not reorder or drop any of the five checks (length/empty, control chars, backslash, leading-slash-not-double-slash, authoritative `url`-crate recheck).

    assert!(validate_return_to("/api/auth/login").is_some());
    assert!(validate_return_to("/api/auth/callback").is_some());
}

```tsx
'use client';

import { usePathname, useSearchParams } from 'next/navigation';
import { TextLink } from './TextLink';

/** Wraps `TextLink` to append the current page's path + query string as a
 * `return_to` query parameter on the login link, so `GET /auth/callback`
 * (`crates/api/src/routes/auth.rs`) can send the user back here instead of
 * always to `SSO_POST_LOGIN_REDIRECT_URL`. See
 * docs/superpowers/specs/2026-08-31-dynamic-post-login-redirect-design.md's
 * Design → Where the return path is captured.
 *
 * A separate Client Component rather than adding these hooks to `TextLink`
 * itself: `usePathname()`/`useSearchParams()` are Client-Component-only
 * hooks, and `TextLink` must stay server-renderable (see its own doc
 * comment) since most of its call sites are Server Components. This
 * mirrors the existing `AuthStatus.tsx` embeds `LogoutButton.tsx` pattern
 * -- a small interactive Client Component leaf inside a server-rendered
 * tree -- which is why this works identically at the two Server Component
 * call sites (`AuthStatus.tsx`, `TicketPanel.tsx`) and the five Client
 * Component ones.
 *
 * Deliberately cannot capture a URL fragment (`#...`) -- a fragment is
 * never sent to the server on any HTTP request, by construction of the
 * URL/HTTP specs; there is no mechanism here or anywhere else that could
 * round-trip one through a full-page OIDC redirect. Known, accepted
 * limitation -- see the design spec's Open Questions. */
export function LoginLink({
  children,
  underline,
}: {
  children: React.ReactNode;
  underline?: 'hover' | 'always';
}) {
  const pathname = usePathname();
  const search = useSearchParams().toString();
  const returnTo = search ? `${pathname}?${search}` : pathname;
  const href = `/api/auth/login?return_to=${encodeURIComponent(returnTo)}`;
  return (
    <TextLink href={href} underline={underline}>
      {children}
    </TextLink>
  );
}
```

## Sequencing notes

- Tasks 1 → 3 → 4 → 5 form the backend's hard dependency chain (migration, then the data layer built on it, then `login()`, then `callback()` in the same file immediately after). Task 2 (`validate_return_to`) has no dependency on any of them and can be done first, in parallel with Task 1 — both are listed early because Task 4 needs both done.
- Task 3's Step 4 deliberately leaves the workspace in a non-compiling intermediate state (the one existing caller of `insert_login_state`, in `routes/auth.rs`, isn't updated until Task 4) — flagged explicitly in that task so a subagent-driven or checkpointed execution doesn't mistake it for a mistake; either do Tasks 3 and 4 in the same session, or accept a red `cargo build` between their two commits.
- Task 6 (`LoginLink`) has no backend dependency and can be built any time, including in parallel with the entire backend chain (Tasks 1–5) — it only becomes functionally meaningful once Task 7 wires it in and the backend tasks are also deployed.
- Task 7 depends only on Task 6 (imports `LoginLink`) — not on Tasks 1–5 being deployed for its own tests to pass (all 7 test files mock `next/navigation` and never make a real network call to the backend), though the feature has no real effect end-to-end until both halves ship.
- Overall recommended order: 1, 2 (parallel with 1), 3, 4, 5, 6 (parallel with 1–5), 7 — backend-then-frontend, matching this repo's existing plan convention (`docs/superpowers/plans/2026-08-31-tracked-trains-list.md`), adapted here to note the two backend-internal parallelization opportunities (1↔2) and the one cross-cutting one (6 alongside the whole backend chain).

## Open questions carried forward from the spec (not resolved by this plan)

1. **No redirect-loop guard.** `validate_return_to` (Task 2) accepts `/api/auth/login`/`/api/auth/callback` themselves as valid same-origin paths — not a security hole, but a plausible confusing-loop edge case the spec flags and explicitly declines to resolve. Task 2 pins this as a passing test (`validate_return_to_currently_accepts_a_return_path_back_into_the_auth_flow_itself`) specifically so a future implementer adding the guard gets a visible test failure forcing an update, rather than silently changing behavior. This plan implements no such guard.
2. **URL fragments (`#...`) can never be captured**, by construction of the URL/HTTP specs — `LoginLink` (Task 6) has no mechanism to include one, and no page in this app was exhaustively audited for reliance on fragment-only state during the design pass. Not a bug this plan can fix; carried forward as a known, accepted limitation.
3. **The `2048`-byte cap on `return_to`** (Task 2's `MAX_LEN`) is the spec's own placeholder, not measured against this app's actual longest real route (candidates like `/lines/[id]` with several query filters, or `/train/[uid]/[date]`, were named but not measured). This plan implements the placeholder as specified rather than researching a tuned value.
4. **Whether to also bound `return_to`'s query-string *shape*** (e.g. an unusually large number of repeated query keys), beyond the flat byte-length cap — the spec notes this was not investigated. Not addressed by this plan.

## Judgment calls this plan made in sequencing (not decisions the spec left open, but choices this plan had to make to turn the spec into an executable order)

- **Split the backend work into 5 tasks (migration / validator / data-layer / login / callback) rather than 2–3 larger ones**, so each task's diff and test additions stay reviewable in isolation and match this repo's established granularity (`docs/superpowers/plans/2026-08-31-tracked-trains-list.md`'s Task 1/Task 2 split for a comparably-sized backend change). The corollary is Task 3's intentional non-compiling intermediate state, called out explicitly rather than silently worked around, since the spec's own code sketch presents `login()`'s and `data/users.rs`'s changes together with no sequencing guidance of its own.
- **`routes/auth.rs`'s first-ever test module was placed to hold both Task 4's and Task 5's tests**, rather than splitting into two modules or deferring testing to an integration suite — this file had zero tests before this plan (confirmed by grep), so there was no existing convention to match; the choice made here mirrors `crates/api/src/auth.rs`'s own single-`mod tests`-per-file shape.
- **Task 6 (`LoginLink`) and Task 7 (the 7 call sites) were kept as two separate tasks, not merged**, per the brief's explicit instruction not to compress "replace 7 call sites" into one vague step — Task 7 alone names all 7 files individually with each one's own before/after diff and its own test-file update, rather than treating them as a single undifferentiated sweep.
